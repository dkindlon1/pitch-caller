# PitchIQ V1.3 — Software & Systems Architecture audit (role: arch)

Auditor: software/systems architect agent. Tip audited: `feat/hitter-v13-final` @ c602f1c. Main: 8bcf909 (fetched, depth 300).
Box: Intel Xeon 2.1 GHz, 2 cores, load average 10–16 the whole time (nine agents). Every timing below was taken under that load.
CPU time (`process.cpuUsage`) is the more reliable number; wall time is 3–5x higher.

## 1. Verdict
**C+.** Engine parity is real and holds today (both parity checks pass, error ~1e-13). V1.3 is not a performance regression.
But the release machinery around it is not ready to ship:
- CI on this branch has never got past its first suite.
- If the code merges as it is, CI on main will check nothing below `tests.py`.
- When the engine throws, the coach gets a frozen screen showing an old call, or a blank one.
- The version label doesn't change between v1.2.3 and v1.3.
- An offline iPad still on the old app goes blank if it opens a D2 game planned on the new website.
Everything that blocks the release can be fixed without changing a single call.

**Merge risk (item 6):** low mechanically. Main 8bcf909 is the merge base, and the branch is **135 commits ahead, 0 behind**, so it's a
fast-forward with no conflicts. Diff: 445 files, +267,310/−5,693 lines. By area: results 211k, hitter_data 26k, data_tables 10.7k,
docs 9.8k, app 1k. Code: `engine.py` +892/−311, `app/engine.js` and `web/lib/engine.js` +225/−66, `index.src.html` +4/−3, `learner.js`/`roster.js`
3 lines, `app/dist` +462/−140, no Supabase migrations. **Merge with `--no-ff`**: then a single `git revert -m 1` undoes it, and c602f1c (the
commit Step 6 recorded) stays in history unchanged. A squash would lose it.

**Rollback (item 5):** the mechanism is sound. `docs/RELEASE_builds_1-4.md` §Rollback uses Vercel Instant Rollback, so git isn't involved.
The service worker caches by content hash, installs the new version in the background, takes over only between games and deletes old caches.
No DB change. Gaps: (1) A3 (D2 plans break old or rolled-back apps); (2) A4 (no way to see which version a device runs; use
`events.doc->'v'->>'data'` = `c756860d96` as the cross-check instead); (3) an offline iPad keeps v1.3 until it's online and reloaded
between games. There is no remote kill switch or engine flag: the tables are baked into `engine_data.json` inside the page, and
`config.json` carries only the project settings.

**iPad extrapolation (not measured on a device).** The repo's own trace (`docs/APP_V2_PROGRESS.md:29`, v1.2 engine, owner's machine):
the first pitch of an at-bat is a 53–85 ms task, and at 4x throttle the p95 is ~480 ms. v1.3 is within ±50% of v1.2 on the same box
(above), so I expect **~50–130 ms on a current iPad and ~0.3–0.7 s on an older one (the repo's 4x stand-in), up to ~2x that for 6-pitch
HS arsenals** with why/intent added on top. Under heavy load or Low Power Mode it can pass 1 s. Every call is a synchronous
main-thread block, so no path hangs indefinitely, but A2/A3 turn any throw into a frozen or blank screen.

- **The full test-app.sh and CI runtime/flakiness.** The brief forbids running the whole suite on this box, and CI has never run it on v1.3 (A1).
  Locally I ran `tests_v13_tables.py` (338 s): `38/41 checks passed`. I filtered out the FAIL names by mistake and didn't re-run it; the build log's §8 lists them.

- **Whether the lost pitches in A2 still reach IndexedDB/Supabase** (`logPlay`) while localStorage reverts. That would leave game state and the DB inconsistent; not traced.
- **Live production state.** Vercel deployments, the service worker versions on real devices, and Supabase game-plan rows with `college_d2` weren't touched (rules).
- **Side effect of my fetch:** the shared `.git` pack grew from 225 MB to ~541 MiB. Ref `refs/audit/main` → 8bcf909 was added in the shared repo.
