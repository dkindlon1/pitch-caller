# Pitch Caller v1.0: report at the Phase 5 pause

Written Nov 6-7, 2026 on branch `v1.0-work` (HEAD `84e7d9c`). Plan: `docs/PLAN_v1.0.md`. Running log:
`docs/V1.0_LOG.md`. Handoff: `docs/HANDOFF_hitter_model.md`. Frontier and diagnostics: `results/tune_v10.md`.

**This is not a completion report. v1.0 is paused and is not on `main`.** Phases 0-4 and 6-8 are built and tested.
Phase 5 has now been tuned twice and no setting passes the bands and the v1.0 scenario gate. Every number below is at
the starting values `KAPPA_T 3, KAPPA_L 1, GUARD_TYPE 0.030`, which remain the shipped ones because no tuned point
qualified.

Three things block finishing, none of them in this branch's control:
1. **The hitting-model work has not merged.** `origin/main` is still exactly tag `v0.9` (`3b9d645`), and `v1.0-work` is
   already based on it, so there is nothing to rebase onto.
2. **GitHub Actions is not running jobs** on this account: every job fails in 1-2 s with "recent account payments have
   failed or your spending limit needs to be increased". "CI is green" cannot be demonstrated until that is fixed.
3. **The v0.9 baseline games are not on this machine**, so the 90-game simulator floor has never been measured for v1.0.

## The headline: the Phase 5 stall is not one problem, it is three

The first Phase 5 run concluded that the remaining gaps were the engine's cost differences, i.e. the hitting model, and
v1.0 was paused on that basis. That was only partly right. After the Phase 9.3 review, two re-fits and a second grid,
the failures split three ways:

| group | bands | whose | state |
|---|---|---|---|
| The usage prior was mis-derived | B1, B2, B5 | the calling side (ours) | **fixed** (`cd4297e`). B2 now passes outright at 25 of 96 grid points; B1's worst miss more than halved |
| The location window is the binding constraint | B13, part of B7 | the calling side, but a limit the plan fixes | **measured, left alone by Drew's call.** B13 reaches 100% at a window of 0.020 |
| Genuinely cost-shaped | B6, B8a, B3, rest of B7 | the hitting model | open, and now the only part that is theirs |

**B13 matters most of these.** It is the one band the plan added expressly to guard against a regression, v0.9 passed it
24/24, and v1.0 does not. The diagnostics show it is purely a location-window effect and needs no hitter math.

**Why widening the window is not a free fix.** B8a moves the other way under exactly the changes that help the others
(80.2% -> 72.9% at window 0.020, 58.3% with the guard off), and even with the guard fully off B6 reaches only 66.5%
against a 98% rule. No window or guard setting passes everything. Drew's call: leave the window fixed.

## Phase 4: converged except the wild pitches

Three rounds, the plan's limit. After round 3, **11 of 12 fitted values move under the 0.01 fixed-point criterion** -
hbp and wild by at most 0.0004 - and walks sit exactly on target at every level (hs 14.06 vs 14.06, D3 11.38 vs 11.38,
D1 10.79 vs 10.79).

The twelfth is the wild-pitch multiplier, and it cannot converge at the 30 games the plan fixes:

| | round 2 | round 3 |
|---|---|---|
| value over the 0.01 criterion | D1 `wp_os`, delta 0.01085 | D3 `wp_os`, delta 0.01148 |
| D1 wild pitches per batter | 0.0209, on target | **0.0149, outside** (-0.60 pts) |
| D3 wild pitches per batter | **0.0305, outside** (+0.31 pts) | 0.0300, within |

The offender swaps levels between rounds and the band verdict flips with it; D1's three rescale passes inside round 3
read 0.0200, 0.0221, 0.0149 on 20-29 wild pitches per ~1340 batters. With 25-40 wild pitches per level the sampling SE
is about 0.4 points, larger than both the +-0.3 point tolerance it is judged against and the 0.01 criterion. **Drew's
call: freeze the round-3 values and treat the wild-pitch band as reported, not gated, the way strikeouts are.**

Strikeouts, reported not fitted, identical in rounds 2 and 3 and inside Drew's drift rule: hs **-1.23** points (his
limit about 2), D3 -0.35, D1 -0.70 (limit 1). HBP is on target at the real-world target mix (4.1-4.2%) and 2.1-2.5% at
the engine's own mix, as he ruled.

## What was fixed along the way (none of it changes a call distribution)

Found by the Phase 9.3 review or by running the suites on a second machine:

- **`scripts/test-app.sh` ordering, twice.** `golden_v09` ran second and fails by design on v1.0, so with `set -e`
  parity, the `app/dist` build gate and every app suite never ran - which is how a stale `app/dist` reached the branch.
  `learn_test`, failing by Drew's decision, then did the same thing. Both known failures now run last; the suite reports
  **14 checks** where it used to report one.
- **`app/dist` was stale** (Phase 7 changed `learner.js` and never rebuilt it).
- **`app/build.py` was not byte-reproducible**: it wrote the dist in text mode, so a Windows build differed from Linux
  on all 9047 lines and the build gate could never pass from a Windows checkout. Verified fixed against a build in the
  `pc-py313` Linux container.
- **`tests_v09_followups.py` could not run on Windows** (platform-encoding reads), and with it running, its
  Python-vs-JS `GUARD_DELTA` check had been silently broken since Phase 3.6, which combined the two guard constants on
  one line and defeated its regex. The missing cross-engine check on `GUARD_TYPE` was added.
- **CR1** crashed in Python and silently no-opped in JS on a matchup key with no spot; **rule-note order** differed
  between the engines (tuples vs joined strings).
- **Parity coverage was thinner than plan rule 7 implies**: `ump_u` was never varied and `usage_by_call` never passed,
  and the comparison ignored `info.rules`, the why line and the plan line. All now covered, and the generator takes a
  seed because cases are drawn in sequence. 4 seeds x 200 cases pass, worst margin 2.83e-11.
- **`tune_v10.py` overwrites `results/tune_v10.md`**, which had silently destroyed run 1's frontier and diagnostics -
  the numbers the handoff was written against. Both runs are now kept in the file.

## What is not fixed, and why

- **Ten enforced bands fail** and no grid point passes. Per plan rule 11 nothing was loosened, no term was added, and
  nothing was tuned outside the stated ranges.
- **B13 is a real regression** against v0.9 and is a location-window effect, not hitter math. Drew's call: leave the
  window fixed, so it stays failing and is recorded for the handoff.
- **B8a** moved the wrong way and conflicts with B3/B6/B7/B13 under every window and guard setting tested.
- **The wild-pitch multiplier** is frozen at round 3 and reported rather than gated; it cannot converge at 30 games.
- **The simulator floor** has never been measured for v1.0.
- **`golden_v10`** is not frozen, because the engine is not final.
- **The CI-tier call sheet and v1.0 scenarios are not wired into `scripts/test-app.sh`** (plan 9.2): both fail, so
  wiring them in would break that suite for a second reason. `scripts/v10_gates.sh` runs both instead.
- **The learner switch** was not retuned; Drew kept the current setting pending Phase 5.
- **The README engine section** is not rewritten, because the tuned constants are not settled.
